# Brain AI v2 data model and migration specification

Version 2.0.0-draft.1. Proposed schema, not executed SQL. IDs are UUIDs internally; existing text IDs remain valid via mapping, never rewritten in place. New wire IDs are opaque strings. All personal FKs include owner_id in the referenced unique key to make cross-owner linkage impossible. All timestamps are UTC timestamptz; preserve source timezone/offset and uncertainty separately. NUMERIC is exchanged as decimal strings.

## Ownership and authorization additions (M01)

`owners(id, status, created_at)`; `principals(id, owner_id, kind:user|device|service, status, auth_version)`; `device_credentials(id, principal_id, secret_hash, expires_at, revoked_at)`; `principal_scopes(principal_id, scope)`; `legacy_owner_mapping(client_id, owner_id, approved_by, approved_at)`. Devices are not owners; two devices can belong to one owner. Provisioning/revocation is controlled administration, never a public unauthenticated registration shortcut. Keys use high entropy and constant-time verification; no raw keys stored server-side.

Add nullable owner_id to raw_events, classified_events, entities, aliases, relations, merges, accounts, financial transactions/evidence, facts, jobs, corrections, reviews, policies, embeddings, insights/digests/intelligence and diagnostics where absent. Build explicit ownership inventory for every installed table/view/function. Backfill from approved client mapping and evidence; unresolved/shared legacy personal records enter quarantine, inaccessible through ordinary APIs. Split personal entities by owner using mapping table `legacy_entity_owner_map(old_id, owner_id, new_id)` and migrate dependent edges/aliases/corrections, preserving original IDs as scoped aliases. Public taxonomy definitions move to a separate table or explicit `scope_kind=taxonomy` relation with no personal text/metadata. Null owner is never a public-data shortcut.

Then validate composite FKs, add NOT NULL for personal rows after quarantine split, add `(owner_id,id)` unique indexes and RLS. Runtime role cannot DDL, bypass RLS or change owner. RLS predicates use transaction-local server-authenticated owner context; API predicates remain mandatory. Maintenance role has separate credentials and audit scope. Revoke exposed-role grants/default privileges on personal tables, sequences and functions; inspect view security and security-definer search_path/EXECUTE. Do not substitute blanket `TO authenticated` for ownership.

## Observation Engine (M02)

| Table | Required fields and constraints |
|---|---|
| source_instances | id, owner_id, connector_kind, provider, account_scope_hash, device_id nullable, policy_id, status; unique(owner_id,connector_kind,provider,account_scope_hash,device scope) with explicit normalized nonnull scope key. |
| observations | id, owner_id, source_instance_id, source_key, latest_revision_no, created_at, deleted_at; unique(owner_id,source_instance_id,source_key); source_key is opaque source identity, not title/content hash. |
| observation_revisions | id, owner_id, observation_id, revision_no, producer_revision_id, producer_sequence bigint, content_fingerprint, canonicalization_version, content JSONB, source_occurred_at nullable, source_updated_at nullable, device_observed_at, received_at server default, change_kind:posted|updated|removed|imported, source_time_uncertainty_ms; unique(owner_id,observation_id,revision_no), unique(owner_id,source_instance_id,producer_revision_id) via source instance column/FK. |
| delivery_receipts | id, owner_id, source_instance_id, delivery_id, revision_id, request_fingerprint, acknowledged_at; unique(owner_id,source_instance_id,delivery_id). Exact replay returns stored receipt. Conflicting delivery ID is 409, never overwrite. |
| delivery_attempts | id, owner_id, receipt_id nullable, delivery_id, received_at, status_code, error_code, request_id; metadata only, no repeated payload or secrets; rejected untrusted attempts have credential-safe operational audit instead. |
| legacy_event_revisions | owner_id, raw_event_id, observation_id, revision_id, mapping_version; unique(owner_id,raw_event_id). |

Server locks observation identity to allocate monotonically increasing revision_no. Producer sequence is persisted before sending and determines content recency, not arrival order. Accept sequence 2 arriving before 1: append both immutable server revisions, but latest effective content remains producer sequence 2. For multiple producers, use separate source_instance identity or connector-provided comparable version; never invent a total source order. A reused producer_revision_id with different fingerprint/sequence returns 409. Duplicate content at a new legitimate sequence is retained as a revision (e.g. A -> B -> A); do not use global unique content hash. Retries reuse producer_revision_id, producer_sequence and delivery_id. New upload attempt is logged separately. Client deletion/removal cannot retroactively erase historical observations.

Fingerprint: SHA-256 over RFC 8785 canonical JSON of `{changeKind, content, sourceOccurredAt, sourceUpdatedAt}`, exact Unicode retained, absent optional fields canonicalized to null by contract version. Delivery time, credentials, title inference, transport metadata and producer/server IDs excluded. Server recomputes; mismatch 422. Version field `jcs-sha256-v1` isolates future changes. Content changes of any evidence field create a new producer revision; timestamps only create a revision when sourceUpdatedAt or content semantics actually changes. `raw` is included inside content; volatile capture diagnostics are outside fingerprint input.

Android source_key is a durable generated instance ID mapped to `(device installation, Android user profile, package, notification key, lifecycle generation)`. Notification key reuse after known removal creates a new generation. Removal persists a tombstone revision referencing previous content; it does not cancel a payment. Restart reconciliation consults persisted mapping and last observed fingerprint. Ambiguous reuse after missed lifecycle boundaries is flagged, not merged based on key alone.

## Facts, canonical events and correction overlays (M03)

`extraction_runs(id, owner_id, revision_id, extractor_version, prompt_version?, model?, policy_version, correction_version, status, started_at, completed_at)`; unique successful run key includes revision/extractor/context/policy versions.

`extracted_facts(id, owner_id, revision_id, run_id, field, value JSONB, data_type, evidence_pointer, span_start?, span_end?, excerpt_hash, method, extractor_version, model_revision?, confidence numeric, uncertainty JSONB, validation_status, supersedes_fact_id?, created_at)`. Evidence pointer is JSON Pointer into immutable content; spans are UTF-16 code units, start inclusive/end exclusive, matching JS/Kotlin; verify excerpt and bounds before promotion. Structured receipt fields may use pointer without span. An LLM-provided quote not in source fails validation. Fact validity: proposed|validated|ambiguous|rejected|user_confirmed. Deterministic method alone does not grant validated status.

Reuse existing correction tables as append-only decisions with owner_id, target revision/fact/canonical ID, field, value, scope:once|rule, version, actor, created_at, revoked_at, expected projection version. Selection layers: active exact-target user decision -> exact applicable user rule -> validated nonconflicting evidence -> uncertain proposal. Conflicting authoritative sources produce review, not arbitrary priority. Preserve original extracted facts and correction history. Automated replay cannot revoke decisions. Broad rules require matching constraints/source and user preview; similarity is insufficient.

`canonical_events(id, owner_id, event_type, lifecycle_status, occurred_start, occurred_end?, time_uncertainty, current_version, retired_at?, merged_into_id?)`; `canonical_event_evidence(owner_id, canonical_event_id, observation_id, revision_id, fact_id?, role, strength, active, decision_id)`. Cardinality many-to-many. Unique(owner,event,revision,fact key,role); normalize optional fact key explicitly for uniqueness. Corrections/merges are audited reversible decisions; losing a projection never deletes canonical identity. `projection_generations(id,owner_id,domain,subject_id,revision_id,input_hash,correction_version,policy_version,producer_version,status)`; unique domain/idempotency key and one published generation per domain/subject through guarded pointer update. Readers see an entire old or new generation, never half.

Processing is per stage: captured -> queued -> running -> succeeded|review|retry_scheduled|dead_letter|cancelled. `review` is terminal for that input until a correction/new revision explicitly creates a new run. Existing raw processing_status becomes a compatibility summary derived from stages; semantic failure cannot reset finance to unprocessed or real-world posted to pending. History retains reason, generation, fence and previous/next values. Stale work for old revision may finish an archival extraction but cannot publish over current projection.

## Financial extensions (M04)

Extend existing financial_transactions and financial_transaction_events, do not create a second ledger. Add canonical_event_id, owner_id, lifecycle_version, lifecycle_status, provider/account/reference identity, occurrence/posting timestamps and confirmed decision ID. Extend evidence with observation_id, revision_id, fact_ids, amount_role, currency_status, native_reference, reference_namespace, evidence_strength and active. Unique(owner,transaction,observation,revision,role) prevents replay duplicates; one observation may support multiple facts/events. Display evidence count means distinct active observations; revision count is separate. Reports aggregate canonical financial rows/legs once, not evidence joins.

Store amounts NUMERIC(24,6) initially; ISO currency exponent registry enforces final allowed precision (UYU/USD two decimals); preserve raw source decimal string, never silently round extra precision. Amount roles: purchase, posted, authorized, balance, available_credit, tax, fee, installment, refund, transfer_debit, transfer_credit. Currency status explicit|account_confirmed|user_confirmed|ambiguous|unsupported. A bare `$` requires verified source/account policy evidence; otherwise ambiguous. Known unsupported ISO currency remains recorded but excluded from UYU/USD totals. UNKNOWN cannot act as a currency match wildcard.

Financial lifecycle: observed -> authorized|pending|declined|posted|review; authorized -> posted|reversed|expired|review; pending -> posted|declined|cancelled|review. Declined/cancelled/expired do not contribute spending. Posted does not become declined because a later notification is vague. Refund/reversal is a linked signed adjustment, with partial refunds allowed; never overwrite historical settled amount. `financial_adjustments(id, owner_id, transaction_id, adjustment_event_id, kind, amount, currency, posted_at, reference)` unique provider adjustment reference when present. Refund sum exceeding original requires review; unmatched refund stays separate reviewable evidence. Transfers have two explicit legs and optional FX linkage, excluded from spending totals; never assume destination amount equals source across currencies. Installment parent and children are linked; reporting uses posted children, never parent+children together. Manual pending plans are not bank-pending transactions.

Matching rules, evaluated in order:

1. Owner/source/native reference namespace/account equal, exact reference plus compatible currency/type/lifecycle -> deterministic link under uniqueness lock. Conflicting amount/currency/reference reuse -> review, no merge.
2. Same observation update -> existing candidate/event link, validated lifecycle transition; preserve transaction ID.
3. Explicit verified cross-provider order/payment mapping -> deterministic link; order with multiple charges requires charge/line discrimination.
4. Fuzzy candidate score: merchant exact canonical 0.25, exact amount/currency 0.25, account/instrument 0.20, compatible source/lifecycle 0.15, time proximity 0.15. Hard mismatches reject. >=0.85 with margin >=0.20 offers high-priority review, 0.60–0.85 review candidate, lower creates separate provisional event. These are initial ranking thresholds, not auto-merge authorization. Time/amount/merchant without strong identity never auto-links. Tune on held-out data; no relaxed threshold to inflate recall.

`financial_match_decisions` retains candidates, features, score, reason, algorithm version, actor and undo decision. Lock owner/account/native-reference bucket with transaction-scoped advisory lock or row lock, re-read before insert and use uniqueness constraints. No native reference: create separate provisional identities; do not invent unique(amount,merchant,time). Verified native reference uniqueness applies only to namespaces known to be transaction-unique. Crash after link before ack replays same unique evidence and effects.

Optional `fx_rates(id,base,quote,rate numeric(24,12),as_of,provider,recorded_at)`; conversions store source amount, rate ID, rounding rule and converted amount. No implicit rate. Report response is grouped original currencies; converted result appears only on explicit request and discloses rate/time. Mobile fixed-reference totals must be removed or explicitly replaced.

## Jobs and fencing (M05)

Extend background_jobs with lease_expires_at, heartbeat_at, fence bigint default 0, owner_id, stage_input_hash, cancellation_version and replay_generation. Attempts have immutable attempt/fence/worker and completion result. Index `(priority,run_after,id)` where status in queued/retry_scheduled; `(lease_expires_at,id)` where running; unique(owner,job_type,idempotency_key,replay_generation). Avoid null-owner uniqueness holes by separating maintenance job scope.

Claim atomically selects ready or expired-running jobs SKIP LOCKED, increments attempt and fence, assigns lease. Expired attempt recorded as abandoned. Default lease 90s, heartbeat 20s, stage deadline 40s; verify current host budget first. Claim only executable capacity (initial 1), not 25 jobs held behind a serial loop. Heartbeat/complete/fail/publish require job ID, worker ID, fence, running status AND unexpired lease; zero-row update means lost ownership, discard output. Publication locks current job row and checks fence within the same transaction as projection changes and downstream enqueue. Checking before a separate commit is insufficient. No external model request inside that transaction.

Failure: retry_scheduled with full jitter min(30min,2s*2^(attempt-1)), honoring bounded Retry-After; default max five attempts (intelligence existing limit may stay two). Invalid content -> review; policy revoked -> cancelled; missing/foreign event -> cancelled + audit; max attempts -> dead_letter. Operator replay preserves previous attempts and increments replay_generation; never resets historical fence. Completion and next-stage enqueue are atomic. Inline v1 compatibility acquires the same lease/fence and cannot settle another worker's attempt. Side effects use unique stage effect keys `(owner,revision,stage,version,input_hash)` plus fenced transaction. Reaper+metrics run each poll; standalone uses same contracts. Crash tests span before claim commit, after claim, after model response, after projection commit before ack, heartbeat failure, expired completion and overlapping cron.

## Embeddings, episodes and connectors (M06–M08)

`embedding_spaces(id,provider,model_revision,dimensions,normalization,tokenizer_version,prefix_version,chunk_version)` unique complete descriptor. Existing knowledge_embeddings gets owner_id, space_id, revision/generation lineage, policy_version, eligible, deleted_at; unique(owner,object_type,object_id,space_id,content_hash,policy_version). Index owner/space/eligible plus appropriate source/time metadata joins. A row can only serve a compatible query; never overwrite one model with another fallback under embedding_version alone. Content hash is checked before inference.

`episodes(id,owner_id,type,current_revision,status:proposed|active|closed|review|retired)`; `episode_revisions(id,owner_id,episode_id,revision,start_at,end_at?,time_uncertainty,rule_version,summary_artifact_id?,confidence,reason)`; `episode_memberships(owner_id,episode_revision_id,canonical_event_id,revision_id,role,confidence,evidence_ids,decision_id)` unique membership. Related entity overlaps remain typed relations; no causal relation generated without explicit evidence. Incremental candidates: same owner, shared confirmed entity/reference and gap <=60min for shopping/work/research, <=24h for travel; purchase/delivery and appointment use shared reference across longer time windows. These windows propose membership only. User split/merge/exclude decisions persist as overlays.

`connector_accounts(id,owner_id,provider,status,token_secret_ref,scope_set,policy_version)`; `connector_cursors(account_id,stream,cursor,version,updated_at)`; `connector_sync_runs(id,owner_id,account_id,start_cursor,end_cursor,status,counts)`; encrypted attachment metadata/hash/ref with source retention. Tokens never in raw_events. Cursor CAS and durable observation writes commit together per page; duplicate delivery safe. Location facts store latitude/longitude precision, radius, observed interval, source/provider and sensor accuracy. Activity is a separate interpreted fact, not a coordinate synonym.

## Indexes and integrity verification

Owner-leading B-tree indexes for observations/source identity, revision ordering, event timestamps, native transaction reference and evidence traversal; GIN for scoped search_vector queries, explicit owner filters before candidate limits. Composite FKs cover evidence, graph, correction, episode and embedding lineage. Check amount/currency/status consistency; finite vector values and exact dimension check. PostgreSQL CHECK constraints cannot enforce cross-table ownership, so use composite FKs and scoped queries/RLS. Build large indexes concurrently in nontransactional migration steps with separately recorded validity checks; do not put CREATE INDEX CONCURRENTLY in the existing all-in-one migration transaction.

## Migration integrity and rollout

M00: catalog verifier inventories pg_class/pg_attribute/pg_constraint/pg_index(indisvalid), pg_policy, role memberships/rolbypassrls, grants/default ACLs, views/security options, procedures/search_path/EXECUTE and schema_migrations. Compare to versioned expected-object manifest including definitions and checksums. Add migration checksum/state/object-verification records without editing applied migration history. Detect filename ledger plus missing table/index/policy as drift. Verify migrations 0037/0038 and all later runtime-created objects explicitly.

M01 ownership nullable -> approved backfill/quarantine -> scoped APIs -> restricted role/RLS -> validate constraints. M02 observations and v1 mapping -> dual-write shadow. M03 facts/generations -> correction replay. M04 financial links/lifecycles -> shadow reconciliation. M05 leases can ship before M02/M03 using legacy event inputs. M06 embedding isolation -> incremental reindex. M07 episodes. M08 connectors.

Migration worker exclusively owns `migrations/`, expected-object manifests and migration runner per integration window. Feature workers propose DDL requirements but do not allocate conflicting migration files. Use the existing runner convention for legacy additions; if Supabase CLI generation is adopted, verify installed help/version and consolidate one authoritative ledger rather than mix unreviewed systems.

Execution steps per migration: isolated clean create, representative upgrade, deliberately partial state, concurrent startup, backup/restore; record lock duration/query plans and count/hash reconciliation; run with direct migration URL only. No request-path repair DDL after compatible rollout; runtime readiness fails with a safe schema-incompatible response and queues remain durable. Repair is a reviewed roll-forward migration that creates all missing verified objects, not a table sentinel or blind ledger insertion. Never auto-drop unexpected objects.

Backfills are owner-keyset paginated (initial 500 rows), checkpointed and idempotent; cap transactions <=5s, tune from measured locks. Keep original raw IDs and financial IDs. Legacy raw rows become one imported revision each; do not claim reconstructed missing updates. Old ambiguous links are flagged for review, never bulk silently unmerged. Shadow counts compare distinct observations, confirmed transaction totals by currency, corrections and citation sources. Cutover uses flags only after independent reconciliation. Rollback disables v2 publication and returns to compatible v1 reads, preserving additive evidence; if old writer would destroy new facts, pause writes instead. Destructive cleanup requires explicit human approval after backup restore proof, signed mapping review and rollback rehearsal. Production restore is disaster recovery with write reconciliation, not the default rollback.
