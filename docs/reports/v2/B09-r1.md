## Roll-forward, rollback and compatibility

Deployment order: provision an isolated PostgreSQL matching the deployment;
restore a disposable snapshot and test old/new writers; apply the reviewed
roll-forward with schema-owner credentials; run the read-only contract checks;
verify a nonowner runtime role cannot CREATE/ALTER and has required DML/RLS
behavior; then deploy the runtime assertion code. Production application is a
separate human-approved operation and was not performed here.

`20261015000000_reconcile_runtime_schema.sql` uses idempotent creates, replaces
functions, restores triggers, expands the learning constraint, and enables RLS /
revokes anonymous access. It retains all user data and historical ledger rows.
It repairs omissions rather than attempting to silently rewrite arbitrary
incompatible existing columns/constraints; structural drift fails reconciliation.
Legacy rows gain source checksums only after objects reconcile.
All concurrently running migration processes must use the new runner; older
runners do not participate in its advisory lock and must be stopped before rollout.

Forward writers retain existing tables, columns and function entry points;
legacy callers receive `repaired:false` plus `verified:true` from readiness
helpers. The historical repair cron URL remains authenticated and read-only.
Old backend code continues on the additive schema with a private role whose
DML/RLS rights have been verified. Public REST roles are intentionally revoked;
deployments depending on their access are incompatible and must be corrected.
Code must not be released before the schema is complete: assertions deliberately
fail closed instead of repairing during a request.

Rollback: roll back application code only after confirming its writer format is
compatible; retain additive schema objects, checksum/attempt ledger and evidence.
Do not delete migration rows, drop tables/functions or re-enable runtime repair.
For a failed concurrent index, inspect persisted attempt status and PostgreSQL
validity first; a separately reviewed operator action must remove/rebuild an
invalid index before retry. An interrupted valid index without a ledger entry
also requires explicit operator reconciliation. Data rollback requires a proven
isolated restore before approval; that restore is currently blocked above.
