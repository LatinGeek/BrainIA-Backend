## R1 — missing source policy fails closed

`src/storage/privacy.ts`:

- New denial reason `source_policy_missing`.
- The policy loop no longer substitutes `DEFAULT_SOURCE_POLICY` for a named source. `sources` and evidence-derived sources are all checked against explicit owner policy rows. A missing row returns a denial before any provider call.
- Owner, purpose, evidence ownership, evidence privacy, processing eligibility and cross-owner checks are unchanged and still run first.
- Denials remain metadata-only in `logPrivacyDenial` (`reason`, `purpose`, `sourceCount`); no owner, source, prompt or payload is logged.
- `DEFAULT_SOURCE_POLICY` remains only for ingest-time processing decisions (`loadSourceProcessingPolicy`), which do not dispatch externally. A source with no row may therefore still be captured, but classification/enrichment/embedding dispatch is local or skipped.
- Proactive insight synthesis now resolves explicit sources from candidate evidence (`eventIds`, and transaction `anchor_event_id`) and unions the owner denied-source list. The daily digest embedding also adds the digest's `eventsBySource` to its authorization. This closes the missing-row case for those owner-invoked derived paths when lineage is resolvable.

## R2 — stale insight/digest embeddings

`src/storage/embeddings.ts`, `src/storage/privacy.ts`, `src/storage/hybrid-retrieval.ts`:

- `upsertEmbedding` looks up the linked insight/digest run and persists `metadata.ownerId`, `metadata.derivedFrom`, `metadata.runId` and `metadata.policyVersion`; `policy_version` is the maximum of the authorization version and the run version.
- `invalidateDerivedWorkForPolicyChange` now marks derived embeddings stale through the joinable run id in addition to the legacy `metadata.source` match. This works for embeddings that never had `metadata.source`.
- The hybrid vector branch now:
  - excludes embeddings marked `metadata.policyStale = true`;
  - excludes embeddings older than the owner's current maximum policy version;
  - excludes insight/digest embeddings whose run is missing or older than an owner policy bump.
- The full-text branch already excluded stale runs from r2 and remains unchanged.

## R3 — JEV event binding

`src/storage/jev.ts`:

- The authorization must include `event.id` in `authorization.eventIds`; a source-only authorization is rejected.
- The stored event row must exist and match the authorization owner and the payload source, and must be `privacy_status = 'standard'` with `processing_allowed`.
- `stillAuthorized` re-evaluates the live policy against the event/source before `fetch`; a policy change during the call path blocks dispatch.
- The wrapper path is preserved by passing the event id at authorization time in `src/storage/classification-assistant.ts`. This is a one-line supporting change outside the literal declared boundary but required to keep real classification working under the stricter JEV gate.

## R4 — inspect graph neighbours

`src/storage/agent-inspect.ts`:

- `loadInspectEntityLineage` now returns per-entity eligibility (`eligibleEntityIds`, `blockedEntityIds`) instead of one aggregate event set.
- An entity is eligible only when it has at least one linked event and **every** linked event belongs to the caller, is `standard` and is processing-allowed. No lineage or ineligible lineage blocks that entity.
- The root must be eligible, otherwise external synthesis fails closed as before.
- Only eligible entities contribute events to authorization.
- `restrictGraphForExternalDispatch` removes blocked nodes and any relation/path referencing a removed node from the external prompt.
- Search-returned entity descriptions are also filtered by the same eligibility set when external dispatch is enabled.
- The local API response (`graph`, `searchResult`) is unchanged, so deterministic inspection still works.

## Remaining limitations

- **Zero-explicit-source dispatch is still possible where lineage cannot be resolved.** `semantic_reconciliation` authorizes only the owner denied-source list; a node set with no attributable source can still dispatch when no policy denies it. Proactive insight and daily-digest embeddings now resolve evidence sources, but candidates/insights with only unattributable evidence remain the same residual. This is a lineage gap, not the missing-policy-row case fixed in R1.
- **Policy-row deletion.** Explicit-source dispatch now denies after a row is deleted (no row ⇒ `source_policy_missing`). Derived paths without an explicit source still cannot detect deletion; staleness is computed from the owner's maximum policy version. There is no application deletion path today.
- **Legacy derived runs with `policy_version = null`** are still treated as non-stale by both retrieval branches, matching r2 behavior. They are not re-stamped by this pass.
- **Route-created insight/digest embeddings** may still be stored without `client_id`, so owner-scoped vector retrieval can omit them (the run link does carry owner metadata). Routes were outside this write boundary.
- **Search relations** are still included in the external prompt when overall authorization succeeds; entity descriptions are filtered, but relation descriptions were not individually lineage-gated in this pass.
- **Real PostgreSQL/RLS/concurrency, pool-role persistence, restore and multi-process job claiming remain BLOCKED.** PGlite proves isolated engine behavior only.
- **E08/E10 and the other v2 suites remain BLOCKED**; no adapter credit.
- Ownerless cron paths remain deterministic/local.
