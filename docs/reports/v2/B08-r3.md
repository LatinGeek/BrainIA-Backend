## 1. Revived-row repair (pre-r2 `attempt_count = 0` with history)

A row revived by pre-r2 code can be `queued` with `attempt_count = 0` while attempt 1 already exists in `background_job_attempts`. The claim used to increment `0 -> 1` and then insert `(job_id, attempt) = (id, 1)`, failing with `23505 duplicate key ... background_job_attempts_job_id_attempt_key` and leaving the job queued.

Fix: both claim statements now use one shared expression instead of `attempt_count + 1`:

```sql
greatest(
  job.attempt_count,
  coalesce((select max(history.attempt)
            from background_job_attempts history
            where history.job_id = job.id), 0)
) + 1
```

This is a lazy repair at claim time, not a destructive backfill and not a migration. A healthy row keeps its current count (the highest history attempt is normally the current/previous attempt, so `greatest` is a no-op); only a rewound row is lifted to its historical maximum before the new attempt is appended. `max_attempts` is still extended by `reviveFailed` exactly as in r2, so the repaired attempt has a budget.

Regression (`tests/v2-jobs.test.ts`, `B08/E07 reviveFailed repairs a legacy attempt_count=0 row before claiming`): two jobs are dead-lettered at attempt 1, then updated to the pre-r2 revive shape (`status=queued`, `attempt_count=0`, attempt 1 history retained). One is claimed through `claimBackgroundJob`, the other through `claimBackgroundJobs`. Both claim successfully as attempt 2 / fence 2, complete, and history is `[1 dead_letter, 2 succeeded]` with no duplicate-key error and no overwritten historical row.

## 2. Stale main-work projection

### Observed ordering before the fix

`executeBackgroundJob` for a classification job called `classifyCapturedEvent`, which opened its own transaction and committed the classification rows plus `correlateFinancialEventWithDb` (canonical financial transaction + evidence). Completion was attempted afterwards. A worker that lost its lease/fence during execution therefore still committed classification and financial main work, even though `completeBackgroundJob` then rejected its stale fence. This is the B08 verification E2 observation (`stale execution after fence 2 still created 1 transaction + 1 evidence row`).

### Fix

`assertJobFence(db, job)` performs a `select ... for share` against the live job row, requiring `id`, `fence_token`, `status='running'`, the same `locked_by`, and a live `lease_expires_at`. It is called **inside** the projection transaction, after the business row lock (`raw_events ... for update`) and before any classification/financial write:

- `classifyCapturedEvent(eventId, { fence })` checks once, immediately before `insertClassifiedEvent` and the in-transaction financial correlation.
- `correlateFinancialEvent(eventId, { fence })` checks at the start of its transaction.
- `job-worker.ts` passes the claimed `BackgroundJob` for `classification` and `financial_correlation`; `appendEvent`'s inline financial projection passes its claim as well.

The `for share` lock is held for the rest of the projection transaction. This makes the fence atomic with the write: a claim that already advanced the fence makes the check throw `StaleJobClaimError` before any main work commits; a claim that has not advanced it yet blocks until the projection commits, then re-evaluates the live row and cannot overwrite the projection in the same fence. The transaction rolls back cleanly on a stale fence; the worker reports `stale` and publishes no effects.

Regression (`B08/E07 stale fence cannot publish classification or financial main work`): claim attempt 1, expire it, claim attempt 2, then execute attempt 1. Execution rejects with `StaleJobClaimError`, `financial_transaction_events` for the event stays at 0, and the current attempt then executes/completes and produces exactly 1 evidence row. The pre-existing `classification retry does not duplicate finance side effects` test still passes (a still-current first execution is allowed to project exactly once).

### What is not fenced

- The guard covers the classification and financial-correlation main-work projections, which are the paths that write canonical financial rows. Embedding, insight, retention, backup verification and semantic enrichment are not wrapped by this guard; they remain fenced only at completion/effect publication as before. Broadening the guard to every job type is a larger refactor and was outside this condition.
- Real multi-connection PostgreSQL remains **BLOCKED** (no Docker daemon). PGlite is a single in-memory engine, so the `for share` serialization argument is code/SQL-level evidence, not a two-session snapshot proof.
- The inline `reprocessEvent` path used by queued-mode captures does not project financial rows (`skipFinancial: true`) and is unchanged.

## Remaining limitations

1. **Real-PostgreSQL concurrency is BLOCKED.** Duplicate-key repair and `for share` fencing are proven on PGlite only. A real two-session run should re-check the claim-vs-projection interleaving.
2. **Projection fence scope.** Only classification and financial correlation main work is fenced. Other job types still rely on completion-time fencing.
3. **Lazy repair only.** Rows are repaired when claimed. No backfill or monitoring counter was added for how many legacy rows are repaired; operators will not see the repair except through attempt numbering.
4. **`reviveFailed` has no route caller.** The latent pre-r2 rows are still not reachable through the public API today.
5. **No schema/contract change.** No migration or `contracts/schema/manifest.json` regeneration was needed.
