## Defect → fix mapping

### N1 HIGH — own accounts rejected by real capture

- The effective event owner is now `coalesce(raw_events.owner_id, raw_events.client_id)`. Real captures populate only `client_id`, so they resolve to the authenticated owner instead of `null`.
- The effective owner is used consistently for account resolution, native-reference matching, duplicate review, advisory locking, and the canonical ledger write. New captured rows persist `financial_transactions.owner_id = effective owner`, so the existing `t.owner_id = a.owner_id` balance join counts them.
- `listFinancialAccounts` and `createBalanceAdjustment` additionally tolerate historical `owner_id`-null transactions whose linked evidence event carries the same authenticated `client_id`. This is a read-only compatibility fallback, not a backfill.
- Foreign-owner accounts are still rejected before any ledger write: they store `account_id = null`, keep `foreign_account_ignored`, expose no foreign label, and cannot change the foreign balance.

HTTP regression added (uses the real `POST /api/v1/capture/wallet` route, authenticated owner headers, and **no** manual `raw_events.owner_id` update):

- after capture, `raw_events.owner_id` is `null` and `client_id` is owner A;
- the materialized transaction has `account_id = account A`, `owner_id = owner A`, and no `foreign_account_ignored`;
- owner A's account balance becomes `-55.00`;
- a bare `$ 12,00` capture against owner A's UYU account becomes `account_confirmed` / `UYU`;
- owner B's account passed by owner A still stores `account_id = null`, records `foreign_account_ignored`, and owner B's balance stays `0`.

### N2 MEDIUM — summary response violated the v2 `FinancialSummary` contract

- `GET /financial/summary` no longer returns `excluded.unknown` or `excluded.unconfirmedAmount`. `excluded` now contains exactly the contract fields `ambiguous`, `unsupported`, and `pending`.
- `from` and `to` are required by the route. Omitting either returns the documented `400 invalid_financial_summary_query` instead of returning `null` timestamps. The response always carries string `from`/`to`.
- Legacy UNKNOWN and unconfirmed accounting is retained as an internal diagnostic through `getFinancialSummaryExclusionDiagnostics`; it is not serialized by the route.
- Regression added: the response top-level keys are exactly `from,to,asOf,totals,excluded,conversion`; `excluded` keys are exactly `ambiguous,pending,unsupported`; `from`/`to` are strings; an omitted range returns 400.

### N3 LOW — unknown amount roles entered confirmed totals

- An unrecognised amount role still stores the reviewable fallback role `posted` and the `unknown_amount_role` review reason, but now sets `amount_confirmed = false`.
- Confirmed summary totals, account balances, proactive insights, and intelligence aggregates already require `amount_confirmed = true`, so these rows stay out of confirmed reporting until reviewed or explicitly corrected.
- The row remains visible in transaction lists with its review reason. No new amount-role value was added, so the existing database check constraint and manifest are unchanged.
- The D2 regression now asserts `amountConfirmed = false` and proves only the explicit posted row contributes to the confirmed UYU total.

## Remaining limitations

1. **E01/E03/E05 unchanged.** E01 still reports 50/450 and its adapter still hard-codes extracted value status `confirmed`; E03/E05 remain blocked. This remediation does not claim those suites pass.
2. **N4 not addressed.** FX approval is still a boolean without four-eyes enforcement, and `fx_rates` RLS has no policy for a restricted runtime role. The current owner-pool deployment is unchanged.
3. **N5 historical data not remediated.** No destructive backfill was run. Historical foreign-account rows, legacy bare-dollar rows, and old ambiguous evidence are not reclassified. The new balance fallback only helps `owner_id`-null transactions that have an evidence event with the matching `client_id`.
4. **Summary range is now mandatory.** Clients that previously omitted `from`/`to` receive `400 invalid_financial_summary_query`. This matches the v2 contract; no implicit default window was added.
5. **N3 review surface.** Unknown-role rows are stored as reviewable `posted` rows with `amount_confirmed = false` and `unknown_amount_role`; there is no dedicated review queue/UI. Adding an explicit `unknown` role would require a migration and contract decision.
6. **Real PostgreSQL remains BLOCKED.** All database execution used in-memory PGlite (`tests/pglite-setup.mjs`). Real-server RLS, role behavior, concurrency, and restore are not certified here.
7. **N1 scope.** The effective owner prefers `raw_events.owner_id` when present and otherwise falls back to `client_id`. This matches the requested `coalesce` semantics; a caller cannot set `owner_id` through the public capture routes.
