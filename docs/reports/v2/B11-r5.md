## R5 — `revalidateDerivedRun`

The r3 read predicate honors `revalidated_at`, but nothing could set it. r5 adds
an internal/admin storage workflow in `src/storage/data-controls.ts`:

```ts
revalidateDerivedRun({ ownerId, runType: "insight" | "digest", runId })
```

It returns either a success record (`revalidatedAt`, `lineageEventIds`) or a
typed rejection:

| Reason | Meaning |
|---|---|
| `run_not_found` | Missing, foreign or invalid owner/run id. Existence is not disclosed and nothing is mutated. |
| `no_live_lineage` | No live, owner-scoped event supports the run. |
| `source_policy_denied` | A live lineage source has no explicit owner policy, or the policy disables egress (`enabled = false` / `send_to_llm = false`). |
| `policy_stale` | The run was derived under an older policy version than the owner's current maximum; regenerate instead. |

All checks run inside one `withTransaction`, with the run row selected
`for update`. `revalidated_at = now()` is written only after every check passes.
Owner scoping is strict (`owner_id = $owner`); there is no legacy/anonymous
fallback for this operator action.

### Live lineage

The lineage branch mirrors `derivedRunReadEligibilitySql`:

- **insight**: event id present in `evidence`, `request` or `response`;
- **digest**: event id present in `request` or `response`, **or** the event
  timestamp falls inside `window_from .. window_to`;
- the event must belong to the same owner, have `privacy_status = 'standard'`
  and `processing_allowed = true`.

Runs without such lineage stay hidden: no timestamp is written and every read
path continues to apply the conservative pre-tombstone rule.

### API surface

The function is exported from the storage layer only. No Fastify route, contract
or UI was added, so it cannot be reached by an ordinary client. An operator or
admin script must call it deliberately (and is responsible for authenticating
the operator outside this storage function).

## Regressions added

### `B11 r5 revalidation rejects foreign, denied-source and lineage-less runs`

Seeds three insight runs for one owner, then a ledger-only tombstone on an
unrelated live event (all three were created before it):

- an otherwise valid run revalidated with a **foreign owner** returns
  `run_not_found` and leaves `revalidated_at` null;
- a run backed only by a live event whose source has `send_to_llm = false`
  returns `source_policy_denied` and stays unreadable;
- a legacy entity-only run with `evidence: []` returns `no_live_lineage` and
  stays unreadable;
- a direct SQL check confirms no `revalidated_at` was written for any of them.

### `B11 r5 a live-lineage run becomes readable only after deliberate revalidation`

Creates an insight and a digest backed by a live event, then tombstones an
unrelated event. Both runs are hidden by the conservative pre-tombstone rule.
After `revalidateDerivedRun` for each run type:

- the result is `revalidated: true`, the reported lineage is the live event id,
  and `revalidatedAt` is strictly after the tombstone;
- `loadInsightRunById` / `loadDigestRunById`, list, history lists and
  `exportPersonalData` serve both runs again;
- the summary text survived the update (the r3 guard did not redact it because
  the payload never referenced the tombstoned target).

The reverse is covered by the first test: a rejected revalidation never makes a
stale run readable.

## Remaining limitations / not closed

- **Acceptance is not claimed.** This closes only the "no revalidation workflow"
  residual, not B11 as a whole.
- **No operator UI or authenticated route.** The function is callable from
  server-side admin tooling only; the caller must enforce operator identity and
  authorization. There is no audit row for a revalidation decision (the existing
  deletion audit covers tombstones, not revalidations).
- **Database update guard still applies.** If the run's lineage payload names a
  tombstoned/hidden target, the r3 `BEFORE UPDATE` trigger redacts the payload
  even though `revalidated_at` is written. Operators should regenerate such runs
  instead of revalidating them; the function reports success because the
  remaining live-lineage and policy checks did pass.
- **Policy-stale runs cannot be revalidated.** A policy bump requires
  regeneration; the function returns `policy_stale` rather than timestamping old
  content.
- **A later tombstone hides the run again.** `revalidated_at` only clears
  tombstones that existed at revalidation time; the predicate compares against
  every tombstone's `created_at`.
- **Text/prose resurrection remains undetectable by id.** Revalidation proves
  live event lineage, not that every sentence originated from that evidence.
- **PGlite only.** Real PostgreSQL RLS/multi-connection behavior and `pg_dump`
  restore remain BLOCKED; E06/E11/E12 remain BLOCKED with no adapter credit.

No commit, dependency install, migration, manifest regeneration or production
database was used.
