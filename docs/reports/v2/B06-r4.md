## What is now enforced

### 2. RLS role switching

`withOwnerRead`/`withOwnerTransaction` always set the transaction-local owner.
They switch to `set local role brainia_runtime` when
`BRAINIA_DB_ENFORCE_RLS=true` (or `{ enforceRls: true }`). The role switch is
**environment-gated on purpose**: B06 did not change every ingestion write to
persist `owner_id` (for example `insertRawEvent` still writes only `client_id`),
so enabling the restricted role unconditionally would make owners lose access
to their own newly ingested rows. The opt-in flag is the reviewed cutover
control; once ingestion writes `owner_id` on every personal row, the flag can be
made the default. This is recorded as deferral D1.

The routed-read regression (`B06 routed reads switch to the restricted role…`)
proves the flag is real at the route boundary: a legacy row with
`client_id = owner-a` and `owner_id = NULL` is returned before the flag and 404/
omitted after it, while the owner's owned event remains visible and owner-b's
event stays invisible. The RLS unit test now also asserts
`current_user = brainia_runtime` inside the scoped transaction.

### 3. Cron and empty-body daily evaluation are explicitly global

- `GET /cron/daily-insights` requires the `jobs` scope (`requireScope`) in
  addition to the CRON secret. It responds with `{ scope: "global", writer: "cron" }`.
- `POST /insights/daily` with an empty body is rejected for an authenticated
  owner principal (`400 owner_scoped_daily_insight_required`) so an owner
  credential can no longer spawn an owner-null run. Cron/global/legacy-unscoped
  principals still run the global evaluation and receive
  `{ scope: "global", writer: "daily" }`.
- Runs produced by either writer are tagged in `request`
  (`{"scope":"global","writer":…}`) while remaining `owner_id = NULL`.
- Owner-facing history reads filter `owner_id is not distinct from <caller>`, so
  these runs are not returned to any scoped owner. The regression inserts a
  global cron insight/digest and verifies neither appears in owner history, and
  verifies the run created by an actual cron request is tagged and excluded.

The global writer still *summarizes all owners* by design (that is what a
global job is). It is now explicit, auditable, and excluded from owner-facing
reads. Admin reads still require an owner scope on owner routes; there is no API
that publishes global runs to owners.

### 4. Legacy null-owner repair (dry-run + apply)

`repairLegacyNullOwnerFinance(db, options)` in `src/storage/data-controls.ts`
covers:

- `financial_accounts`
- `pending_financial_transactions`
- `insight_runs`
- `digest_runs`

Policy (non-destructive):

- A row is assignable only when its **own evidence** names exactly one owner:
  accounts from the owner/evidencing events of transactions that reference the
  account (or an already-owned pending row); pending rows from an already-owned
  account; insight runs from event ids present in
  `evidence`/`request`/`response`; digest runs from persisted event ids or from
  a window whose events belong to one owner.
- An explicit operator `mapping[rowId] = ownerId` overrides evidence.
- Ambiguous or evidence-free rows stay `NULL` and are written to
  `owner_quarantine` with reason `legacy_null_owner_requires_review`.
- Apply (`dryRun: false`) only runs `update … set owner_id = $2 where id = $1
  and owner_id is null`; payloads, ids, evidence and balances are untouched.
  Successful assignments are recorded as `legacy_null_owner_assigned`
  (`owner_quarantine.status = 'remediated'`).
- Dry-run is the default. No rows are modified in dry-run.

Operator invocation (no new script file, so the write boundary is preserved):

```bash
# dry-run
npx tsx -e "import {pool} from './src/storage/postgres.ts'; import {repairLegacyNullOwnerFinance} from './src/storage/data-controls.ts'; console.log(JSON.stringify(await repairLegacyNullOwnerFinance(pool), null, 2)); await pool.end();"

# apply, optionally with an explicit reviewed mapping
npx tsx -e "import {pool} from './src/storage/postgres.ts'; import {repairLegacyNullOwnerFinance} from './src/storage/data-controls.ts'; console.log(JSON.stringify(await repairLegacyNullOwnerFinance(pool,{dryRun:false,approvedBy:'ops-ticket',mapping:{'<row-id>':'<owner-id>'}}), null, 2)); await pool.end();"
```

Regressions cover: dry-run does not mutate; single-owner account/pending/insight
repair applies; a two-owner account stays `NULL` and is quarantined; a
window-digest spanning two owners stays `NULL`; the repaired account is visible
to its owner and invisible to the other owner.

## What is still deferred

- **D1 — `owner_id` writes on ingestion.** `insertRawEvent` (and other
  event-store writes outside this worker's boundary) still persist only
  `client_id`. Until that changes, `BRAINIA_DB_ENFORCE_RLS` stays opt-in and
  legacy `client_id`-only rows remain an availability concern under enforcement.
- **D2 — Financial and privacy mutations.** Only the list/detail/export reads
  named in the task were moved onto owner transactions. Create/update/delete,
  merge, false-positive, balance adjustments, privacy patch/delete and source
  policy writes still use the pool plus their existing owner predicates.
  Owner checks for those remain route/repository-level.
- **D3 — Graph traversal query.** `src/routes/graph.ts` performs an RLS-enforced
  root-visibility preflight and retains the owner post-filter, but
  `getEntityGraph` itself still queries the pool because
  `src/storage/graph-repository.ts` is outside this worker's write boundary.
  The route does not leak foreign graphs; the traversal is not yet executed by
  the restricted role. The graph cache remains keyed by entity/depth, so the
  route-level filter is what protects cached results.
- **D4 — `GET /privacy/export` under enforcement.** Source policies are still
  keyed by `client_scope` with `owner_id NULL` (`upsertSourceProcessingPolicy`
  is not wired to the owner transaction), so under
  `BRAINIA_DB_ENFORCE_RLS=true` the export returns an empty `sourcePolicies`
  array. This is a visibility loss, not a cross-owner leak.
- **D5 — Remaining surfaces.** `/semantic/*`, `/agent/*`, `/operations/*`,
  `/entities/resolve`, alias/review routes, entity merge, and background workers
  keep their existing scoping; they were not moved onto owner transactions in
  this pass.
- **D6 — Public taxonomy remains writable by authenticated owners** by design
  (B06 verification condition 3), unchanged here.
- **D7 — Real PostgreSQL and E06/E11.** PGlite only; concurrency, pool-role
  persistence, restore and production RLS behavior are still BLOCKED. E06/E11
  remain BLOCKED (270 cases). No B06 conformance credit is claimed.

## Rollback notes

- **RLS cutover:** unset `BRAINIA_DB_ENFORCE_RLS` (or pass `{ enforceRls: false }`).
  The transaction-local owner is still set, but the role stays the table owner,
  restoring pre-r4 visibility while keeping the scoped transaction shape.
- **Route wiring:** each wrapped read is a local change; reverting the route to
  call the repository with its default pool restores the previous behavior.
  Repository signatures are additive (new trailing optional `db`), so no caller
  changes are required.
- **Cron/daily:** removing the `jobs` scope check and the
  `owner_scoped_daily_insight_required` guard restores the previous behavior.
  Existing null-owner runs remain tagged with `request.scope = "global"`, which
  is harmless.
- **Legacy repair:** the apply step is additive. To undo an incorrect
  assignment, set `owner_id` back to `NULL` for the specific reviewed row and
  reset its `owner_quarantine` row (`status = 'quarantined'`). No payload,
  balance, evidence row or identifier was changed by the repair, so no data
  reconstruction is needed.
