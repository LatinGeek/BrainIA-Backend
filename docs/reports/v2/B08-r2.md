## R1 — serialized claims, live-lease fence

### Implementation

- `CLAIMABLE_JOB_SQL` is the single claimability predicate:
  `queued/retry_scheduled and run_after <= now()` OR `running and lease missing/expired`.
- `claimBackgroundJob` acquires the same transaction-scoped advisory lock as
  `claimBackgroundJobs` before its `SELECT ... FOR UPDATE SKIP LOCKED`. Both paths are
  now single-writer on `brainia:job-claim`; the lock is released at commit and no model
  or request work runs under it.
- The poller's outer `UPDATE ... FROM selected` now has
  `and ${CLAIMABLE_JOB_SQL}` in addition to `job.id = selected.id`. PostgreSQL re-checks
  the live target row for that predicate (EvalPlanQual) when the row was concurrently
  updated and committed, so a candidate selected from an older snapshot is rejected if
  it is now `running` with a live lease. The inline claim's outer `UPDATE ... FROM target`
  carries the same re-check.

### Regressions

`B08/E07 poller re-checks the live row and cannot re-claim an inline live attempt`

- Takes the poller candidate snapshot while the job is queued.
- Wins the job inline at fence 1 with a 60 s lease.
- Runs the production-shaped outer `UPDATE` with the shared guard: `rowCount = 0`; the
  job stays `running`, `locked_by = inline-racer`, same fence and attempt.
- Control on a second job: the pre-fix id-only predicate re-claims the live row
  (`rowCount = 1`, fence advances), proving the guard is the discriminator. The control
  job is then cancelled.

`B08/E07 concurrent inline and poller claims produce exactly one live attempt`

- Five rounds of `Promise.all([claimBackgroundJobs(...), claimBackgroundJob(...)])` for
  one job. Exactly one path wins each round, with `attempt_count = 1`, `fence_token = 1`
  and exactly one attempt row; the winner completes.

**Real multi-connection PostgreSQL remains BLOCKED.** PGlite is a single in-memory
engine, so these are function-level/SQL-level reproductions, not two sessions with
independent snapshots. `contracts/schema/verify.test.mjs` still reports
`realPostgresConcurrency: BLOCKED` and no Docker daemon is available. Condition 2 of the
verification report is mitigated in code and covered by predicate-level regressions, but
is not closed until a two-connection PostgreSQL test exists.

## R2 — new tables are service-internal and default-deny

`20261017160000_job_service_table_lockdown.sql`:

- Enables RLS on `background_job_leases` and `background_job_replays`.
- `revoke all` from `public` and, guarded by `pg_roles`, from `anon` and `authenticated`.
- Deliberately defines **no** owner column and **no** policy: these are scheduling
  internals, not owner-scoped user data. Service access is through the table-owner/admin
  worker connection; the table owner bypasses RLS by default (FORCE RLS is not used).
- Deliberately does **not** grant `brainia_runtime`: no owner-scoped request path reads
  these tables, and the migration that granted all *existing* tables predates them. If a
  future owner-scoped path needs them, it must add a scoped grant and a policy.

Regression `B08/E07 service lease and replay ledgers are RLS default-deny with no public
grants` asserts `relrowsecurity = true` for both tables, zero `pg_policies` rows, and zero
non-owner ACL entries (covers `anon`, `authenticated`, `PUBLIC`, `brainia_runtime`).

The schema manifest was regenerated because a migration changed: 49 migrations / 1816
catalog objects. `schema:verify` and `verify.test.mjs` both accept the new baseline.

## R3 — reviveFailed preserves history

`enqueueBackgroundJob(..., reviveFailed: true)` previously set `attempt_count = 0` while
leaving attempt 1 in `background_job_attempts`; the next claim reused attempt 1 and the
`on conflict ... do update` overwrote the dead-lettered attempt (the verifier observed
`dead_letter` attempt 1 becoming `running` at fence 2).

Now:

- `attempt_count` is preserved; the fence is preserved.
- `max_attempts = greatest(max_attempts, attempt_count + 1)` so the preserved attempt
  still has one budget slot; `dead_lettered_at`, leases, completion and error are cleared
  as before.
- `recordClaim` no longer upserts attempt history. Attempt numbers advance monotonically,
  so the next claim inserts `attempt_count + 1`; a collision now fails the claim
  transaction loudly instead of rewriting history.

Regression `B08/E07 reviveFailed preserves attempt/fence history instead of resetting it`
dead-letters attempt 1 at fence 1, revives, then claims attempt 2 at a new fence and
asserts the historical row is still `dead_letter` with its original fence, while attempt
2 completes. `reviveFailed` is exported but has no route caller; this regression covers
the reachable repository API.

Note: revive intentionally does not write a `background_job_replays` ledger row and does
not increment `replay_generation`; that ledger is reserved for operator replay. If revive
becomes an operator path, it should be routed through `retryBackgroundJob` instead.

## Remaining limitations / not closed

- **Real multi-connection PostgreSQL (R1) is still unverified.** The advisory lock and
  outer-UPDATE re-check are code-visible and covered by SQL-level regressions, but two
  independent sessions, `SKIP LOCKED` timing, advisory-lock blocking and RLS role
  persistence remain BLOCKED without a real PostgreSQL server. Verification condition 2
  is mitigated, not certified.
- **Stale main-work writes remain open** (verification probe E2): `executeBackgroundJob`
  for classification/finance, embedding, correlation, insight, reconciliation, retention
  and backup work still commits outside the completion fence. This was outside the r2
  confirmed conditions and was not changed.
- **E07/E03 remain BLOCKED**: no crash-schedule adapter or finance lifecycle corpus; the
  suite is repository-level PGlite evidence only.
- **Cooperative cancellation remains**: the stage deadline is a `Promise.race`; the
  underlying DB/provider promise is not cancelled.
- **RLS is default-deny but not FORCE**: the worker/table owner bypasses RLS. If the
  runtime is deployed under a non-owner role, the deployer must confirm table ownership
  (or add an explicit worker role/grant); a future blanket
  `grant ... on all tables` would re-grant these tables and `schema:verify` would flag
  the ACL drift.
- **`reviveFailed` budget semantics**: preserving history required extending
  `max_attempts` by one attempt. This is a deliberate semantic choice; the API is still
  unused by routes.
- **Manifest and test writes** are outside the literal original B08 reservation; they are
  supervisor-authorized per R4 and required for `schema:verify` and the regressions.
