## What changed

### Schema (one additive migration)

`migrations/20261017140000_job_leases_fences.sql`:

- `background_jobs`: `lease_id`, `fence_token bigint default 0`, `lease_expires_at`, `heartbeat_at`, `dead_lettered_at`, `last_attempt_finished_at`, `replay_generation default 0`.
- `background_job_attempts`: `lease_id`, `fence_token`, `replay_generation`, `heartbeat_at`; widened status check to include `abandoned`.
- New `background_job_leases` immutable lease history (`acquired/expires/heartbeat/released`, fence, attempt, replay generation, release reason).
- New `background_job_replays` operator replay ledger (previous/next generation, status, attempt count, fence and max attempts, reason/operator).
- Partial ready/lease-expiry indexes plus fence lookup indexes.

No column is dropped, no row is rewritten, and existing job ids/statuses/attempts are preserved. Legacy `running` rows have a null lease and are treated as expired by the next claim.

### Claim, fence and publication

`src/storage/job-repository.ts`:

- One SQL statement per claim (inside a transaction, `FOR UPDATE SKIP LOCKED`) selects ready `queued`/`retry_scheduled` jobs and expired `running` jobs.
- Capacity is computed from active unexpired leases: `globalCapacity` (default 1), `perOwnerCapacity` (default 1), and the requested batch limit. A worker can no longer claim 25 jobs behind a serial loop.
- Per-owner scope is `coalesce(owner_id, client_id, '<global>')`; legacy null-owner maintenance work shares a global scope.
- Each claim increments `attempt_count` and `fence_token`, assigns a new `lease_id`/expiry, records the attempt, opens a lease-history row, and marks the prior running attempt `abandoned`.
- `heartbeatBackgroundJob`, `completeBackgroundJob` and `failBackgroundJob` all require job id, current fence, worker id, `running` status and an unexpired lease. A zero-row guarded update raises `StaleJobClaimError` before any effect or attempt/lease mutation.
- `completeBackgroundJob(job, effect)` runs the guarded status update, the downstream-enqueue/publication callback and attempt/lease release in one transaction. A failing effect rolls back completion and the enqueue.
- `failBackgroundJob` uses bounded exponential backoff with equal jitter (`retryDelayWithJitterMs`), honors a bounded numeric/header/date `Retry-After`, and dead-letters at `max_attempts` with `dead_lettered_at`.
- `retryBackgroundJob` is now an operator replay: it preserves the attempt count and fence, increments `replay_generation`, extends the attempt budget, releases open leases as `replayed` and writes `background_job_replays`.
- `settleInlineBackgroundJob` (v1 compatibility) must acquire the same lease/fence before settling; it can no longer settle a different worker's live attempt.

### Worker and inline path

`src/storage/job-worker.ts`:

- `executeBackgroundJob` now returns effects instead of enqueueing them immediately. Classification/semantic downstream work is published inside `completeBackgroundJob`.
- `processBackgroundJobs` is a bounded loop shared by the cron route, operations route and standalone script. It stops claiming at the host deadline (default 45 s, `BRAINIA_JOB_HOST_DEADLINE_MS`), executes with a per-stage deadline (default 40 s), heartbeats the lease (default 20 s), and reports stale attempts separately.
- Stage deadline expiry fails the fenced attempt (retry) rather than acknowledging success. A stale completion is never reported as success.
- Overlapping cron invocations are safe through leases, global/per-owner active-claim bounds, and a transaction-scoped advisory lock held only for the short capacity/claim statement. The lock is released at commit; no model work runs under it.

`src/storage/event-store.ts`:

- Inline classification and the queued-mode financial fast path now acquire the same classification lease/fence. The inline embedding (and, for the queued fast path, semantic) downstream enqueue is published in the completion transaction.
- If a cron/operations worker already owns the live attempt, the request path skips settlement instead of overwriting it.

`src/routes/operations.ts`:

- `/operations/jobs` also returns lease/replay metrics.
- `/operations/jobs/:id/replays` exposes replay history.
- Retry/replay accept an operator reason/requested-by and go through the replay ledger.

`vercel.json` was intentionally not changed: the host deadline is application-bounded, and this revision does not assume a Vercel plan's `maxDuration` entitlement. `src/scripts/process-jobs.ts` needed no change because it already calls the unified `processBackgroundJobs` contract.

## Compatibility and rollback

- **Additive rollout**: the migration only adds nullable/defaulted columns, tables and indexes. Existing job rows keep their ids, statuses and attempt numbers. New columns default to `fence_token = 0`, `replay_generation = 0` and null leases.
- **Legacy running rows**: a `running` row with no lease is treated as expired and can be reclaimed. This is intentional recovery for jobs stranded by the pre-B08 worker, but operators should expect their first post-migration claim to increment the fence and record the prior attempt as abandoned.
- **Old/new writer coexistence**: do not run an old worker and a new worker concurrently. An old worker can claim only `queued`/`retry_scheduled` rows and does not honor leases, so it could run a job that a new worker later treats as expired. Rollback sequence: stop new cron/worker invocations, let active leases complete or expire, then start the old worker. The schema remains readable by old code because all new columns are nullable/defaulted.
- **Rollback**: no destructive downgrade is required. Leaving the additive tables/columns in place is safe; application rollback is sufficient. Do not drop lease/replay history while jobs are paused if audit evidence is needed.
- **Contract**: the reviewed schema manifest must be deployed with the migration. `schema:verify` fails closed on drift. The API contract bundle is unchanged.

## Remaining limitations

- **E07/E03 are still BLOCKED** in `test:v2`: the harness has no integrated crash-schedule adapter or finance lifecycle corpus for these suites. The evidence above is repository-level PGlite simulation, not the 20×100 E07 matrix or two-process PostgreSQL termination tests.
- **PGlite cannot certify real PostgreSQL concurrency**: it is a single in-memory engine. `SKIP LOCKED`, multi-process lease races, role/RLS persistence and server restart semantics require a real PostgreSQL instance matching deployment.
- **Host cancellation is cooperative**: the stage deadline uses `Promise.race`; an underlying provider/DB promise may continue after timeout. Its fenced completion and downstream publication are suppressed, and finance/classification writes remain idempotent, but the process must still exit within the host budget. Verify the deployed Vercel plan's duration limit before relying on the default 45 s deadline.
- **Finance projection is not fully inside the completion transaction**: classification still materializes the financial projection through the existing event-store path before job completion. Retry/consolidation tests show no duplicate canonical finance row, but a stale worker can perform an idempotent projection write after losing its lease. Moving that publication under the job fence would require broader event-store/financial changes outside this B08 reservation.
- **Legacy owner scope**: background jobs do not consistently set `owner_id`; per-owner capacity uses `coalesce(owner_id, client_id, '<global>')`. Legacy null-owner maintenance jobs share a global scope. Owner backfill for jobs remains a separate reviewed step.
- **New internal tables have no RLS policy**: `background_job_leases` and `background_job_replays` are service-internal and are not exposed through routes, but they are not added to the B06 owner-isolation policy list. Access remains through the existing worker/admin DB role.
- **No real dead-letter/operator replay runbook test**: replay history and budget extension are covered at repository level; operational alerting and replay authorization remain deployment concerns.
- Independent verification is required. This report does not claim acceptance.
