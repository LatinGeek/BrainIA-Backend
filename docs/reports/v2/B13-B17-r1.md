## Implemented behavior

The additive Fastify plugin serves the 19 authorized operations over existing
raw events, finance, privacy and job storage. Capture commits its immutable
revision, durable receipt, owner-attributed raw event and existing classification
job in one owner transaction. Delivery replay returns its original receipt;
producer-revision duplicates receive a duplicate receipt; conflicting identities
fail without losing prior revisions. Producer sequence chooses the current
revision, while every arrival retains a distinct immutable revision number.
Batch results preserve input order with independent item transactions.

Strict Zod validation enforces the published content shapes, exact decimal text,
JCS SHA-256, positive int64 sequence text and UTF-8 limits. All personal responses
use no-store and request IDs. AES-GCM cursors bind owner, operation and filters,
with exclusive positions. Foreign resources return 404. Callback request logging
is disabled so provider codes/state are not written by Fastify's request logger.

Bearer auth accepts configured owner device tokens and the single-client legacy
bootstrap key, without changing the v1 header credential path. Global keys never
borrow an owner. Published operation scopes are checked at the plugin boundary.
The coordinator resolved a scope/contract discrepancy explicitly: the sealed
ErrorObject enum is authoritative, so missing scope and disabled features return
403 `forbidden` with the reason in `message`; no new wire enum values were added.

## Migration, compatibility and residual limitations

- Ten new owner-isolated v2 tables store source instances, observations,
  revisions, receipts, correction target overlays, corrections, queries, export
  snapshots, export audits and connectors. Owner policies/grants protect all ten.
  The migration adds only the required source policy columns and narrowly grants
  runtime access to existing owner tombstones, approved FX and metadata-only
  policy audit insertion. A private boolean quarantine helper avoids exposing
  the quarantine ledger to runtime callers.
- Legacy backfill stores one imported revision per legacy raw event, idempotently,
  preserving the full original row in `legacy_payload` and original timestamps.
  Unknown/quarantined ownership stays invisible. No historical producer identity
  is invented in storage. Mandatory wire producer UUID/sequence/fingerprint for
  an imported revision are deterministic **import transport metadata**, not a
  reconstruction of historical producer revisions. Arbitrary v1 raw extensions
  remain internal because the published v2 content schema is strict.
- New sources require owner/type/source provisioning in `v2_source_instances`;
  there is no public enrollment endpoint. Existing v1 captures remain unchanged;
  legacy observation backfill is migration-driven, not a new v1 writer hook.
- The existing external egress gate has one shared `send_to_llm` control. V2 maps
  it conservatively to `externalModelsAllowed && externalEmbeddingsAllowed`, so
  either denial prevents external upload; model-only permission does not force
  a provider call. Queries always make zero provider calls in this implementation.
- Corrections are durable v2 overlays; v1 remains unchanged. Broad reusable rules
  are stored in review and are not automatically applied. Unsupported legacy
  fact field mappings cannot be corrected through the typed v2 fact operation.
- Episodes/email/activity/location/connectors remain disabled. V1 generated
  prose without verified v2 citation provenance is ineligible as a v2 artifact;
  export omits it instead of inventing verified citations. Unknown non-ISO legacy
  finance currencies are excluded from transaction DTOs and counted in summary
  exclusions; no currency is guessed.
- Export snapshots expire after 15 minutes. Every replay rechecks visibility;
  physical cleanup of expired snapshots/queries/revisions must be integrated
  with the production retention/deletion worker before a deletion feature gate
  can be claimed. The immutable revision trigger permits only explicit privileged
  privacy erasure. This task excludes deletion creation and claims no such gate.
- Set a shared `BRAINIA_CURSOR_SECRET` for cursors across instances/restarts;
  without it a process-random key intentionally invalidates old cursors.
- Before deployment, the migration checksum/object manifest under
  `contracts/schema/` needs separate regeneration and review: the migration runner
  checks that manifest, and it is outside this worker's authorized write scope.
  The published API contract bundle remains unchanged. No production PostgreSQL,
  deployed service, mobile client or OAuth provider was exercised.
