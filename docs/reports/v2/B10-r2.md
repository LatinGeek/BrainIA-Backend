## Defect → fix mapping

### D1 HIGH — cross-owner account attachment

- `linkFinancialTransactionForEvent` now resolves both `accountId` and `destinationAccountId` against the **event owner** before any ledger write. Foreign, missing, or currency-mismatched accounts are dropped from the write and recorded as `foreign_account_ignored`, `event_account_not_found`, `account_currency_mismatch`, or the destination equivalent.
- Ambiguous-currency promotion now uses only the already owner-verified account currency.
- `listFinancialAccounts` and `createBalanceAdjustment` now require `t.owner_id is not distinct from a.owner_id`; another owner’s transaction can no longer change a balance or expose an account label.
- Regression: owner A event with owner B `accountId`/`destinationAccountId` stores `account_id = null`, adds `foreign_account_ignored`, leaves B’s balance at `0`, and A’s list/detail exposes no B account label. An actually owned account still attaches and confirms the account currency.

### D2 HIGH — unsafe same-shape auto-merge

- Fuzzy amount/time/merchant matching no longer creates or updates a canonical transaction. Consolidation now requires the verified native-reference path (`native_reference_match`).
- Same-shape observations without identity evidence create separate rows and receive `possible_duplicate_pending_review` for review.
- Unknown amount roles are preserved as `posted` **with** `unknown_amount_role` review evidence instead of silently merging.
- Native-reference conflict, replay, and scoped-reference merge behavior is unchanged.
- Regressions: two clear same-shape observations stay separate (two UYU rows, total 200 not 100); a real shared native reference still merges deterministically (3 evidence, one 50.00 total).

### D3 HIGH — unverified `currencyConfirmed` bypass

- Removed all trust in raw `currencyConfirmed`, `currency_confirmed`, and `userConfirmedCurrency`.
- Bare `$` / bare number without currency evidence now uses currency `UNKNOWN` with `currency_status = 'ambiguous'`; the repository projection also normalizes any legacy ambiguous row to `UNKNOWN` for reads.
- Only explicit ISO/symbol evidence or an owner-verified account can confirm currency. Caller payloads cannot.
- Regression: `$ 777,00` + `currencyConfirmed:true` stays `UNKNOWN`/`ambiguous`, contributes nothing to confirmed totals (`excluded.ambiguous = 1`).

### D4 MEDIUM — ambiguous currency in insight/LLM aggregates

- Proactive spending, recurring-spend, and taxonomy spending queries now require a confirmed currency status, `amount_confirmed = true`, and `currency <> 'UNKNOWN'`.
- The intelligence aggregate query applies the same filters, so it cannot emit an ambiguous `$` as a confirmed UYU total.
- Regression: prior UYU 100, current explicit UYU 200+50, current ambiguous `$300` yields insight/aggregate current **250** (not 550), previous 100, count 3.

### D5 MEDIUM — negative amounts

- Contract amounts are nonnegative magnitudes. Negative event amounts are normalized by kind (`abs`) with explicit `negative_amount_normalized_by_kind` review evidence, so an expense cannot report a negative expense/positive net.
- Regression: `-100,00 UYU` expense stores `100.00`, reports expense `100.00`, net `-100.00`.

### D6 MEDIUM — decimal parsing

- `parseLocalizedMoneyDecimal` now validates grouping strictly and rejects locale-ambiguous single separators.
- Rejected: `1.733`, `1,733`, `100.000`, `1.2.3`, malformed group sizes. Accepted: `1.733,00`, `1,733.00`, `1.733.000,00`, ordinary 1–2 digit decimals.
- Regression covers parser output and a candidate built from `100.000` returning `null` instead of `100000`.

### D7 MEDIUM — uncertain evidence demoting confirmed evidence

- Canonical `amount_confirmed` now only moves forward (`amount_confirmed or new`); uncertain evidence can no longer flip a confirmed row to false.
- Candidate review reasons are appended to the canonical row, so the uncertain observation remains inspectable.
- Regression: confirmed `100,00` + precision-excess `100.0000` with the same reference keeps the confirmed row, keeps `amountConfirmed = true`, keeps the 100.00 confirmed total, and reports `unconfirmedAmount = 0`.

### D8 LOW — legacy UNKNOWN exclusion accounting

- `GET /financial/summary.excluded` now includes `unknown`, counting legacy `currency = 'UNKNOWN'` rows that are not already counted as ambiguous/unsupported.
- Regression: a legacy UNKNOWN row is absent from totals and counted as `excluded.unknown = 1`.

### D9 LOW — fx_rates RLS/approval/immutability

- New additive migration `20261017220000_fx_rate_governance.sql`:
  - adds `approved`, `approved_at`, `approved_by`;
  - enables RLS and revokes `public`, `anon`, `authenticated`;
  - rejects conversion through an unapproved rate (`fx_rate_unapproved`, HTTP 409);
  - blocks update/delete of an approved rate with an immutable-approved trigger.
- Regression: unapproved rate is rejected; approving enables conversion; post-approval rate update and delete both fail.
- New migration SHA-256: `dbf0a623066489dc4247c892002e2ebe75d1c7495f9ba604da3a9629a52c86e9`.

## Remaining limitations

1. **E01 adapter ownership.** The adapter still marks every extracted amount `confirmed` and reports one purchase value. Fixing it requires an edit outside this boundary. Currency extraction itself now abstains correctly for all 100 ambiguous-dollar cases.
2. **Historical bare-dollar rows.** The fix is forward-only. Legacy rows already rewritten to `UYU`/`explicit` by migration 0017 are not destructively reclassified; a reviewed backfill plan is still needed.
3. **Real PostgreSQL.** RLS and the immutable-approved trigger are exercised only under PGlite. Real server role behavior, concurrency and restore remain BLOCKED.
4. **D1 HTTP coverage.** The regression drives the same `linkFinancialTransactionForEvent` path used by `/events` and both wallet capture routes, but this run did not repeat an authenticated HTTP wallet probe.
5. **Review queue surface.** `possible_duplicate_pending_review` and `unknown_amount_role` are stored review reasons; no dedicated review UI/queue was added.
6. **FX approval is boolean, not four-eyes.** `approved_by` is recorded as a column but not enforced by policy; any writer with table access can approve a rate. The trigger protects approved rows from later mutation.
7. **D5 normalization.** Negative expense/income amounts are normalized by kind rather than rejected; raw text remains available in `raw_amount_text`.
8. **Refunds and multi-currency conversion** remain out of scope (`refunds = 0.00`, E03/E05 BLOCKED as before).
