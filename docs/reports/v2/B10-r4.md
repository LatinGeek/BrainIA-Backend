## Defect

The E01 adapter emitted every extracted amount value with `status: 'confirmed'`, regardless of currency evidence, role, or amount precision. That contradicted the B10 finance rules: a bare `$` is `UNKNOWN`/ambiguous, an unrecognised role cannot be a confirmed posted movement, and excess precision cannot be confirmed. It made the 100 `currency-ambiguous` cases fail even though the application already abstains correctly (transaction currency `UNKNOWN`).

## Fix - adapter value inspection

The adapter is still a read-only observation of current application code. Amount **candidates** still come only from `classifyEvent` entity drafts; the adapter does not invent amounts the application did not extract.

For each extracted amount text it now derives:

- **Currency from the value's own evidence**: explicit `UYU/USD/EUR/GBP`-style three-letter codes and `€`/`£`; `U$S`/`US$`/`USD$` become `USD`; a bare `$` and a bare number stay `UNKNOWN`. Unsupported codes are not confirmed.
- **Role from the containing sentence**: `saldo/balance/disponible/available` -> `balance`; `comisión/commission/fee/cargo/impuesto/tax` -> `fee`; `gastaste/gasto/compra/purchase/pagaste/pago/payment` -> `purchase`; otherwise `unresolved` (and only then the existing transaction candidate fallback, `purchase`).
- **Status from the B10 rules**, reusing `parseLocalizedMoneyDecimal`, `decimalPlaces`, `currencyExponent` and `isSupportedCurrency` from `src/domain/money.ts`: `confirmed` only when the currency is explicit/supported, the amount parses, precision does not exceed the currency exponent, and the role is resolved. Ambiguous currency, unsupported codes, unresolved roles and precision excess are `uncertain`.

The transaction projection (amount/currency/merchant) is still read exactly as the application produces it; it is not corrected in the adapter. That keeps the merchant/amount recall gaps visible instead of masking them.

- Currency abstention stays perfect: `unknownCurrencyAbstention = 100/100`; `currencyHardGate = true`.
- **Amount recall gap:** 50 of 400 expected transactions are missing because the English `Purchase ...` notification is not classified as an expense (`multilingual`, 25 `en` + 25 `mixed` cases). The remaining amount-recall denominator is not affected by the multi-amount balance/fee values, which the harness measures through `transaction.amount`, not `values`.
- **Multi-amount value/merchant gap:** all 200 `multi-amount` cases still fail. The application extracts only the first amount entity and its merchant label absorbs the trailing balance/fee sentence (`SYN-MERCHANT-0. Saldo UYU 9.999,00. Comisión UYU 2,00`). The fixtures expect three amount values and a merchant-only label. Fixing this requires classification/entity-extraction work outside the adapter and outside this condition.
- **Merchant precision/recall:** 200 of the 350 promoted merchant labels are polluted by trailing balance/fee text, giving 0.429 precision; the 50 English misses reduce recall to 0.375.
- Precision remains 1.0 for amount and currency: the adapter never promotes a guessed currency or amount.
