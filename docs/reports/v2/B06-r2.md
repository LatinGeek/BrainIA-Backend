## What changed

### 1. Hybrid retrieval owner filters (`src/storage/hybrid-retrieval.ts`)
- Entity text candidates now require `entity.owner_id = caller` (or public `domain`/`concept` taxonomy) and exclude `visibility = 'hidden'`.
- Relation text candidates require `relation.owner_id = caller`; facts keep `client_id`; insight and digest candidates require `insight_runs.owner_id` / `digest_runs.owner_id`.
- Embedding candidates now require `client_id is not distinct from caller` instead of admitting all `client_id IS NULL` rows, and still apply event/entity/fact visibility checks.
- Graph expansion filters both the neighbour entity and the traversed relation by owner (public taxonomy remains readable) before adding graph candidates.
- A null caller (admin/global or disabled local mode) remains intentionally unscoped.

### 2. Privacy export insight/digest owner filters (`src/storage/data-controls.ts`)
- `exportPersonalData` now adds `owner_id is not distinct from $1` to `insight_runs` and `digest_runs`; owner A no longer receives B's runs.
- `setEntityVisibility` now takes the caller owner and only updates an entity when it is caller-owned, public taxonomy, or a legacy null-owner entity linked to one of the caller's events.
- Export of entities still uses event linkage/public taxonomy rather than `entities.owner_id`; this is unchanged and listed as a remaining gap.

### 3. `insight_runs` / `digest_runs` owner persistence
- New migration `migrations/20261017120000_owner_runs.sql`: adds `owner_id`, owner/created indexes, enables RLS and an `owner_isolation` policy using `public.brainia_current_owner()` on both tables. Additive only; no destructive rewrite.
- `insertInsightRun` / `insertDigestRun` write `owner_id`; `listInsightRuns`, `listDigestRuns`, `loadInsightRunById`, `loadDigestRunById` filter by owner.
- `/insights`, `/insights/history`, `/insights/history/:id`, `/insights/daily`, `/digests`, `/digests/history`, `/digests/history/:id` pass `ownerScope(request)` on read and write.
- Remaining: `src/storage/proactive-insights.ts` background synthesis/digest writers (used by `/cron/daily-insights` and the empty-body `/insights/daily` path) still insert without `ownerId`, so those runs are owner-null and not visible to a scoped owner.

### 4. Explore graph admin scope; entity graph owner filtering (`src/routes/graph.ts`)
- `/graph` taxonomy projection stays public; the explore projection now calls `requireScope(request, "admin")` instead of returning personal graph data to any authenticated owner.
- `/entities/:id/graph` returns `404 entity_not_found` when the root entity is owned by another owner, and strips foreign-owned nodes, relations, and paths from the response before it is sent.
- Filtering is performed in the route after the storage query, not inside `graph-repository.ts`; graph storage remains global for other callers. Explore is therefore admin-restricted rather than owner-filtered.

### 5. `entities/resolve` owner filter (`src/routes/entity-resolve.ts`)
- Matches are post-filtered to canonical entities owned by the caller (or public `domain`/`concept` taxonomy). A B-owned id no longer returns a match to A.

### 6. Aliases/review lists and ownership pre-checks (`src/routes/entity-aliases.ts`, `src/storage/entity-alias-repository.ts`)
- `listEntityAliases` joins `entities` and filters by alias owner or the owning entity.
- `listEntityReviewQueue` filters by review owner or the joined entity owner.
- `POST /aliases` checks `entityOwnedBy`; `POST /review/aliases/:id/resolve` and `POST /review/aliases/:id/ignore` check `reviewOwnedBy` (review owner, or null-owner review whose event belongs to the caller) before mutating.
- Public taxonomy entities are still writable by any owner by design; created alias rows still rely on entity/event ownership rather than their own `owner_id`.

### 7. Metrics admin scope (`src/routes/metrics.ts`)
- `/metrics` and `/metrics/quality` now call `requireScope(request, "admin")`; client-key owners and jobs/cron principals receive `403 insufficient_scope`. Disabled local/test mode remains unscoped.

### 8. Financial merge, entity visibility, review resolve ownership
- `POST /financial/transactions/:id/merge` loads **both** the canonical and duplicate transaction through the owner-scoped `loadFinancialTransactionById`; a foreign duplicate returns `404` before the merge.
- `PATCH /privacy/entities/:id` calls the owner-aware `setEntityVisibility` (see item 2).
- Review resolve/ignore ownership is enforced in item 6.
- `/entities/:id/merge` now pre-checks both entity ids against the caller owner (public taxonomy allowed) before merging.

### 9. Financial owner persistence (`src/storage/financial-transaction-repository.ts`, `src/routes/financial-transactions.ts`)
- `createFinancialAccount`, `createManualFinancialTransaction`, `createPendingFinancialTransaction`, and `createBalanceAdjustment` write `owner_id`; routes pass `ownerScope(request)`.
- Executing a pending transaction carries the pending row's owner into the created transaction.
- Reads (`listFinancialAccounts`, `listFinancialTransactions`, `listPendingFinancialTransactions`, detail loads) apply owner predicates.
- Remaining: list and patch ownership helpers still accept `owner_id IS NULL` for legacy rows created by the pre-fix bug; those rows remain mutually visible/mutable until a reviewed backfill is applied.

### 10. Cron pathname matching fix (`src/auth.ts`)
- The hook now strips the query string (`url.split("?")[0]`) and matches a `cron` path segment with `/(^|\/)cron(\/|$)/`. `?x=/cron/` no longer produces a cron principal.
- Cron routes still perform their own `CRON_SECRET` check; cron keeps `jobs` scope and no owner, so owner-scoped routes reject it via `ownerScope`.

## Security notes

### Confirmed defects from the prior rejection
The ten defects listed in `B06-verification.md` (hybrid retrieval leak, privacy export leak, insight/digest history leak, unscoped entity graph, unscoped resolve, alias/review leak and mutation, privacy entity mutation, financial merge bypass, ownerless financial writes, metrics aggregate leak, cron pathname confusion) each have a corresponding code change above. They are remediated at source level only; **they have not been independently re-probed or accepted**.

### Conditional risks
- Legacy rows with `owner_id IS NULL` are still treated as shared by several predicates (`listFinancialAccounts`, pending list/patches, alias/review fallbacks, entity graph neighbours). Pre-fix ownerless rows therefore remain a cross-owner risk until backfilled and validated.
- Background insight/digest generation writes owner-null runs; a scoped owner will not see them, and an admin will.
- Public taxonomy entities can be mutated (visibility/alias/merge target) by any authenticated owner by design; whether that is acceptable is a product decision, not proven safe here.
- Disabled auth mode still trusts a caller-supplied client-id header; production defaults (`NODE_ENV=production`/`VERCEL=1` or `BRAINIA_REQUIRE_AUTH=true`) protect the deployed path, but an explicit `BRAINIA_REQUIRE_AUTH=false` deployment would remain unsafe.
- Entity graph filtering happens in the route, so any future direct caller of `getEntityGraph` bypasses it.
- Cron retains a valid principal on any path containing a `cron` segment; routes that forget `ownerScope` would accept it.

### Unverified assumptions
- PGlite is not a real PostgreSQL server; concurrency, role persistence, `pg_dump`/restore, and production RLS behavior are blocked.
- E06/E11 remain BLOCKED (270 cases), so the v2 harness does not establish coverage.
- The existing 4 authorization tests were not extended for the rejected surfaces; remediation evidence is code inspection plus the unchanged suite.
- Snapshot attribution still mixes B04/B05/B06 changes; B06-only attribution is inferred.
