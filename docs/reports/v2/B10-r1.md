## Required steps → implementation

### 1. Exact decimal / amount-role / currency evidence

- `money.ts` now parses and computes money as decimal strings backed by `BigInt`:
  `parseLocalizedMoneyDecimal`, `normalizeDecimal`, `addDecimal`, `subtractDecimal`,
  `multiplyDecimal`, `compareDecimal`, `quantizeDecimal`, `absDecimal`, `sumDecimals`.
  No monetary arithmetic uses IEEE-754. `parseLocalizedMoneyNumber` remains only as a
  deprecated numeric projection; storage, matching, balances, FX and reports use decimals.
- Amount roles are carried end-to-end: `amount_role` on transactions and evidence.
  Supported roles include `purchase`, `posted`, `authorized`, `balance`,
  `available_credit`, `tax`, `fee`, `installment`, `refund`, `transfer_debit`,
  `transfer_credit`, `converted`, `destination`; the role is read from provider
  fields and defaults deterministically to `posted`.
- Currency provenance is recorded as `currency_status`
  (`explicit | account_confirmed | user_confirmed | ambiguous | unsupported`) and
  `currency_provenance` (`explicit_currency_code`, `explicit_usd_notation`,
  `ambiguous_dollar_symbol`, `account_currency`, `user_edit`, …).
- Original source text is preserved in `raw_amount_text`. Excess precision is not
  silently accepted: the stored display amount is quantized and the observation is
  marked `amount_confirmed=false` with `amount_precision_excess` review evidence.
- Converted evidence is stored separately (`converted_amount`, `converted_currency`,
  `fx_rate_id`, `fx_rate`) and is only persisted as converted when an approved rate id
  is present. Reports always total the original amount in its original currency.
- Manual amounts accept exact decimal strings as well as legacy numbers; number input
  is converted via its decimal representation, not float arithmetic.

### 2. UNKNOWN wildcard and bare-dollar promotion removed

- `findMatchingFinancialTransaction` no longer contains
  `$3 = 'UNKNOWN' or upper(t.currency) = 'UNKNOWN'`; currency matching is exact.
- A bare `$` / bare number without currency evidence is `currency_status='ambiguous'`
  with `ambiguous_currency` review evidence, and is excluded from confirmed totals.
  For backward compatibility with the existing `domain.test.ts` display assertion the
  legacy `candidate.currency` value remains `UYU`, but the record is stored/read as
  **ambiguous**, never as a confirmed UYU total, and never matches a confirmed row.
  This is the one compatibility compromise in this revision (see Limitations).
- An owned account with a supported currency is the only automatic promotion
  (`account_confirmed`), and only when the account's `owner_id` matches the event owner
  (or both are legacy null).
- Known ISO codes outside `SUPPORTED_CURRENCIES` (for example JPY) are stored as
  `unsupported`; they remain evidence and are excluded from all confirmed totals.

### 3. Distinct evidence count and scoped native-reference locking

- Evidence counts use `count(distinct evidence.id)` in the projection and
  `count(distinct evidence.id)` in the link/merge recalculation. Prior `count(*)`
  join fan-out can no longer inflate `evidenceCount`.
- Native references are parsed from provider keys (`reference`, `providerReference`,
  `transactionReference`, `nativeReference`, …) with an explicit namespace
  (`referenceNamespace`, account id, or source).
- Reference matching is scoped by owner (with the B06 legacy-null fallback through the
  anchor event's `client_id`). Advisory locks are scoped to
  `finance-ref:<owner>:<namespace>:<reference>` when a reference exists, and fall back
  to `finance-owner:<owner>` otherwise.
- Reference reuse with a compatible amount/currency/role/kind links deterministically;
  a conflicting amount/currency/role/kind creates a separate row with
  `native_reference_conflict` review evidence instead of merging.
- Fuzzy amount/time/merchant matching now requires confirmed currency, confirmed amount,
  exact role and exact currency. Different non-null native references never fuzzy-merge.
  A unique partial index `(owner_id, reference_namespace, native_reference, amount_role,
  kind, amount, upper(currency))` enforces scoped reference uniqueness for owned rows.

### 4. Reports grouped by original currency, no implicit FX

- New `GET /financial/summary` (served under the configured API prefix, currently
  `/api/v1`) returns `totals[]` grouped by `upper(currency)`, each with
  `income/expense/refunds/net/transactionCount`, plus
  `excluded { ambiguous, unsupported, unconfirmedAmount, pending }`, `asOf`, and
  `conversion:null`.
- Totals aggregate canonical `financial_transactions` rows once; no evidence table is
  joined into the sum.
- `conversionTo` without `fxRateId` is rejected with `400 invalid_financial_summary_query`.
  With an approved `fx_rates` row the exact rate is applied with `multiplyDecimal` and
  half-up quantization; conversion is limited to a single original-currency group,
  otherwise `409 fx_rate_scope_unsupported`.
- Ambiguous/unsupported/amount-unconfirmed/native-conflict rows are excluded from totals
  and from account balances.

### 5. B06 owner behavior and B04 correction overlay preserved

- Owner filters in list/detail/summary/accounts are preserved, including the legacy
  null-owner evidence fallback.
- `updateFinancialTransactionContext` keeps the correction snapshot/record path and now
  accepts exact decimal strings; `amount_confirmed` becomes true on an explicit amount
  edit, and a user currency edit marks `currency_status='user_confirmed'`.
- Merge/hide/false-positive behavior and hidden-evidence retention are unchanged.

### E01 observation (not claimed as acceptance)

E01 failures report `transaction.merchant` containing trailing balance/fee text and only
one `purchase` value, while the fixture expects the merchant-only label plus separate
`balance`/`fee` values. The adapter (`tests/v2-harness/current-adapter.mjs`) derives
`values` from `classifyEvent` entity drafts and the merchant from the unchanged
`pickMerchantLabel` path; neither is a B10 write reservation. This appears to be a
pre-existing E01 adapter/classification completeness gap rather than a B10 regression,
but I did not run a clean pre-B10 baseline because the worktree was already dirty. This
report therefore records E01 as FAIL/BLOCKED-gap, not as B10 pass evidence.

## Limitations / open items

1. **Bare-dollar legacy field.** For compatibility with the existing domain test,
   `candidate.currency` still displays `UYU` for a bare `$`; the safety guarantee comes
   from `currency_status='ambiguous'`, review evidence and exclusion from totals. A
   future mobile/API cleanup should move that legacy field to `null`/`UNKNOWN`.
2. **Ambiguous rows remain listable.** They are returned with explicit status and
   review reasons; only confirmed totals exclude them. No review queue/UI was added.
3. **FX scope.** Conversion supports one original-currency group and one approved rate
   id per request. Multi-currency conversion requires a separate approved design; it is
   rejected (`fx_rate_scope_unsupported`) rather than guessed.
4. **Refunds/adjustments.** The v2 `financial_adjustments` lifecycle is not implemented
   by B10; `refunds` is reported as `0.00` and E03 remains BLOCKED.
5. **Native reference namespaces** are heuristic (explicit namespace, account id, or
   source). Provider-specific normalization and duplicate-reference adjudication remain
   future work.
6. **RLS.** Request routes still use scoped queries rather than RLS enforcement; B06's
   owner model is preserved but production RLS validation remains BLOCKED.
7. **Real PostgreSQL.** All evidence is PGlite/in-memory; real-server concurrency,
   restore and non-owner role tests remain BLOCKED.
8. **E01** remains FAIL for the adapter/classification gap above; E03/E05 remain
   BLOCKED as expected.
