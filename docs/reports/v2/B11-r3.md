## R1 — read-time eligibility for legacy runs

Legacy r1 tombstones are now honored at read time. No row is backfilled and no
migration is required for existing rows.

`src/storage/search-repository.ts` exports `derivedRunReadEligibilitySql(table,
alias)`, one SQL predicate used by every run read path:

1. a direct `insight`/`digest` tombstone for the run id makes it ineligible;
2. a run **created at/before any tombstone of the same owner** is ineligible,
   even when its payload never named the deleted target (the conservative r1
   upgrade rule);
3. a digest whose `window_from..window_to` **overlaps a tombstoned event's
   timestamp** is ineligible;
4. a run is eligible again only when `revalidated_at` is **strictly after** the
   covering tombstone;
5. after any owner tombstone, the run must still persist **explicit live-event
   lineage** (an event id in `evidence`/`request`/`response` that resolves to a
   standard, processable event of the owner). This keeps a summary-only row
   written before the r3 insert guard ineligible.

Applied to:

| Read path | Where |
|---|---|
| Owner-facing list | `listInsightRuns`, `listDigestRuns` (`insight-repository.ts`, `digest-repository.ts`) |
| By-id | `loadInsightRunById`, `loadDigestRunById` (same files) |
| Hybrid text retrieval (insight/digest branches) | `hybrid-retrieval.ts` |
| Hybrid vector retrieval (insight/digest run join) | `hybrid-retrieval.ts` |
| Route-level hybrid post-filter | `filterEligibleRetrievalResults` (`search-repository.ts`) |
| Personal-data export | `exportPersonalData` (`data-controls.ts`) |

This covers `/insights/history`, `/insights/history/:id`, `/digests/history`,
`/digests/history/:id`, `/retrieval/hybrid` and `/privacy/export`.

`migrations/20261017190000_deletion_run_read_eligibility.sql` adds nullable
`revalidated_at` columns to `insight_runs` and `digest_runs`. Existing rows stay
`null` (never revalidated), which is why no data migration is needed.

## R2 — unlinked summary replay is rejected

The same migration replaces `brainia_block_deleted_derived_run()`. On INSERT,
once the owner has any tombstone, the row must reference at least one **currently
live event of that owner** in `evidence`/`request`/`response` (the summary is
deliberately not accepted as lineage). Otherwise the trigger returns `null`, so
both the repository helpers (`insertInsightRun`, `insertDigestRun`) and direct
SQL writes are rejected.

This closes the exact r2 probe shape: `summary` + `evidence=[]` + `query=null`
(and, for digests, `window_from/window_to=null`, `request/response={}`) after
`deletePersonalData(mode="delete_all")`. A legitimate post-deletion run remains
writable when it carries explicit live event lineage.

## Remaining limitations / not closed

- **Over-invalidation by design.** The mandated conservative rule hides all
  pre-tombstone insight/digest runs for an owner after any deletion, including
  runs unrelated to the deleted evidence, and a window digest is invalidated
  when its window merely overlaps a tombstoned event. This is intentional
  fail-closed behavior, not precision.
- **Revalidation is a column without a workflow.** `revalidated_at` is honored
  by reads but no operator/UI flow sets it yet. A run can only become eligible
  again through an explicit future revalidation write.
- **`digests.ts` `relatedInsights` is outside this write boundary.** Digest
  generation still selects `insight_runs` with only a direct-tombstone filter,
  so a legacy run could be echoed as `relatedInsights` in a newly generated
  digest response (`src/storage/digests.ts:297-317`). It should apply the same
  predicate in a follow-up change.
- **Text/prose resurrection is still undetectable by id.** A post-deletion
  insert may carry live event lineage but prose copied from deleted content;
  neither the trigger nor the read predicate can classify that text.
- **PGlite only.** Real PostgreSQL RLS, multi-connection role behaviour,
  deadlocks and `pg_dump` restore are still BLOCKED. E06/E11/E12 remain BLOCKED
  with no adapter credit.
- **Restore gate remains deployment-configured** (`BRAINIA_RESTORE_MODE`), with
  operator-asserted ledger completeness.
- **Graph cache is in-process only**; cross-instance caches rely on the 30 s TTL.
- **Finance preservation** still protects only transactions with another
  `financial_transaction_events` row.
- **Hybrid post-filter is route-level** for callers requesting insight/digest
  objects; the r3 SQL predicate now also covers the internal text/vector
  branches, so the post-filter is a second line rather than the only one.

No commit, dependency install or production database was used.
